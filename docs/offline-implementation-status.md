## Phase 5: snapshot bootstrap and cursor pull (2026-10-23)

- Engine now exposes authenticated, site and actor scoped `POST /api/v1/offline/bootstrap` and `POST /api/v1/offline/pull` for configured DocTypes. Bootstrap materializes full permitted records, including child rows, from one repeatable-read database snapshot and the matching transactional-outbox sequence boundary. Pages survive Engine restart for 24 hours. Final page returns a pull cursor.
- Pull advances through the transactional outbox in source-sequence order. It returns current permitted records or tombstones for deletions and rows that became inaccessible. Cursor and snapshot tokens are tied to site, actor, selected DocTypes and configuration generation; expired or mismatched tokens require rebootstrap. Cursors expire after 30 days. Expired server snapshots/cursors are pruned when a new snapshot starts. A generic capabilities endpoint exposes the current configuration generation; Android checks that the schemas/navigation it downloaded match the snapshot generation before installing it.
- Existing tenant system schemas migrate with bootstrap version 26. The first device run exposed that the version marker had not been bumped; that was fixed before the successful rerun.
- Android stages each page with a durable checkpoint, resumes interrupted downloads, and installs the final snapshot and cursor in one Room transaction. Pull applies changes/tombstones and advances its cursor atomically. Pending edits are retained as visible conflicts when their server row disappears. The app stops using offset REST refresh for covered DocTypes. Existing installations without a cursor automatically download a new snapshot after authenticated restore; expired cursors trigger rebootstrap.
- Validation: Engine integration test covers immutable pagination while a new record is created, subsequent pull, delete tombstone, and expired-cursor response. Android tests cover interrupted bootstrap/resume, pending-edit preservation on tombstone, rollback of malformed pull pages, and configuration-generation mismatch. Contract generation/check passes for the new versioned DTOs. Maestro downloaded the retail workspace on the final APK and Engine (20:56), confirmed a saved cursor on the Pixel 8, and opened a Product created by a separate authenticated client after pull. The retail owner lacks delete permission, so on-device deletion was not asserted; deletion was verified in the isolated Engine integration test.
- This completes the selected-DocType snapshot and change cursor path. Capability declarations for offline actions, immediate permission purge policy, and device verification across other DocTypes remain separate work.

## Phase 4: production record push (2026-10-23)

- Engine now exposes authenticated, site-scoped `POST /api/v1/offline/push` for bounded batches (1–50) of `record.create` and revision-checked `record.update`. Each operation is executed through the existing kernel, whose idempotency receipt and business write share a transaction. The response contains an operation ID, `acked`/`conflict`/`rejected`/`deferred` status, canonical record on success, and replay indicator. A failed operation does not stop another operation in the batch.
- The Android transport sends new record operations through this endpoint and validates the receipt identity before acknowledging its local outbox entry. v3 legacy operations and POS actions retain their original wire identity and route.
- Integration validation confirms a rejected record followed by a valid record, replay after a lost response returning the same canonical ID, and exactly one server record. Android JVM tests pass. The updated Engine and APK were installed; Maestro created `TEST-PUSH-20261023-2020` through the app and observed its server-assigned `PROD-` ID.
- The mobile dispatcher currently sends one operation per HTTP batch. The kernel receipt is recovered by replaying the same operation, so a separate receipt lookup endpoint is not yet available. Database leases, cross-process dispatch, and action/POS push are still outstanding. This is the record push slice of phase 4, not its entire planned surface.

## Implemented

- Room v4 with additive migration from SQLiteOpenHelper v1/v2/v3. Existing encrypted cache, payloads, and idempotency keys are retained. Legacy draft rows migrate safely and are cleared when the workspace opens. Migration has a real v3 database regression test.
- Separate local record repository and remote transport contracts. Lists/details read local records; list screens observe Room flows. Network refresh updates the baseline while retaining queued local edits.
- Record saves commit the local projection and durable operation atomically. Both connection states use this save path. Acknowledgements retain the list, map local IDs to server IDs, preserve later edits/drafts, and retain operation history.
- New record mutations use Kora's existing kernel API and expected_version concurrency token. Existing legacy operations retain their original REST request path and key. Resource read projection now exposes _version in Engine source.
- One application-scoped sync mutex serializes foreground and WorkManager drains. Interrupted sent operations remain replayable. Operation payload and resolved target are frozen before the first send; dependent local references resolve through canonical IDs.
- Per-operation queued/sent/acked/conflict/rejected/discarded state, persistent errors, retry backoff, correction and discard/use-server UI. Rejections block only the affected record chain.
- Workers receive the exact origin/site/actor in immutable input and check active workspace identity. Sync verifies authenticated actor before dispatch. Removed hardcoded queue migration and automatic session copying between server addresses.
- The shared schema-aware serializer includes nested child-table arrays and typed values. Mobile form drafts were retired on 2026-10-24.
- POS captures a durable local sale projection and action before network dispatch, preserving its reference-derived server idempotency identity. Pending sales appear in ordinary Sale records.
- Explicit workspace download of every REST page, schemas, child schemas, accessible static linked dependencies and optional page manifests. Completion/failure and last download are visible. Missing optional custom manifests do not fail the download.
- App startup restores the local workspace before remote authentication finishes. Cached reads no longer deliberately wait for a failing network request.
- Stable form input accessibility descriptions and test IDs for Maestro.

## Protocol work still required before declaring the entire architecture implemented

The Engine now provides record push, snapshot bootstrap, and cursor pull. A separate receipt lookup HTTP endpoint does not yet exist.

- The selected-DocType snapshot and change cursor are implemented. Permission changes are detected on pull or snapshot page access; a complete immediate device purge policy for revoked coverage still needs definition. Schemas/navigation are fetched separately but pinned to the snapshot's configuration generation. Uncovered DocTypes retain the compatibility REST refresh path.
- The local Engine was rebuilt/restarted with the resource `_version` projection update. Other Engine deployments need that update before editing previously downloaded records safely. The mobile client refuses new unversioned updates rather than silently overwriting another edit. New-create receipts already supply the kernel modified token.
- Offline payment settlement is not implemented; the local sale represents a pending server action. Configured POS sales and Stock Adjustments project cached Product quantity locally and reconcile it after server acceptance. Product stock is read only for ordinary updates, though initial Product creation can still set a starting quantity; imported inventory and privileged non-UI integrations need separate ledger coverage. Server-derived reports still require refreshed server data; local report calculations remain separate planned work.
- Endpoint aliases still require verified stable server identity before transporting existing pending work to another origin. No automatic cross-origin transfer is performed.
- A complete offline authorization expiry/purge policy, exportable backup/recovery UX, and automatic schema migration of pending payloads remain to be implemented.
- Multiple Android processes are not supported by the in-process dispatcher lock. The app currently runs its UI and workers in one process; a multi-process configuration would require database leases.

These limits must remain visible in release notes and acceptance claims. A successful offline Product test does not prove every doctype/action works offline.
